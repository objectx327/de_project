## Путь данных
**Постановка задачи**: Интернет-магазин хранит заказы в базе данных, получает платежи через API, а возвраты выгружает в CSV. Руководителю нужен ежедневный отчёт о заказах, платежах и возвратах за предыдущий день.

1. Источники - API платежей, CSV с возвратами, данные по заказам из БД
2. Загрузка данных из источников - настройка регулярной загрузки данных в хранилище
3. Staging - промежуточный слой для предварительной подготовки данных к последующей обработке - очистка, дедубликация, приведение данных к единому виду
4. DWH - объединение и хранение согласованных данных по заказам, платежам и возвратам, выстроенные в аналитическую модель
5. Трансформации - преобразования данных, например объединение заказов и оплат по ключу, расчеты сумм и количества и прочие расчеты
6. Витрина - набор связанных таблиц с данными по конкретной предметной области для дальнейшего использования в построении отчетов
7. Отчет - сводные данные для дальнейшего анализа

Для текущей задачи предварительно выбираем **ELT** подход, т.к. можно выгрузить данные источников из БД, csv, API в базу и хранить в исходном виде, а уже после выполнять их очистку, объединение и преобразование непосредстенно в хранилище. Этот подход позволит сохранить исходную детализацию для будущих иных аналитических задач.

| Роль               | Задача        |
| ------------------ |:-------------:|
| Data Engineer      | Настройка регулярной загрузки в хранилище данных платежей через API, возвратов из CSV, заказов из БД |
| Analytics Engineer | Построение модели данных хранилища и подготовка витрины интернет-магазина|
| Data Analyst       | Формирование требований к показателям и построение ежедневного отчета на основе витрины |

**Вопросы для уточнения инженером:**
* У разработчика API платежей: Время готовности источников к загрузке, частота обновления, инкремент или фулл, атрибутный состав и типы данных, pk
* У бизнеса: что именно считать заказом, платежом и возвратом, трактовка статусов, содержание и зерно отчета, период отчетного дня, время, к которому нужна итоговая отчетность


### Процесс подготовки поставки:
1. Изменения разрабатываются на DEV-контуре. 
2. Далее проводится тестирование определенной версии решения на TEST-контуре. 
3. После того, как поставка проходит тестирование, она переносится на PROD

Разделение сред позволяет исключить возможное негативное влияние на регламентные процессы на PROD и безболезненно откатить версию до стабильной в случаях, когда это необходимо. На один заказ order_id = 2006 в order_items приходится две позиции с общей суммой 300 EUR:
|order_id|items_amount|item_count|
|--------|------------|----------|
|2006|300.00|2|

В то же время на один заказ приходится две записи с успешной оплатой в payments:
|order_id|paid_amount|paid_count|
|--------|-----------|----------|
|2006|300.00|2|

Из-за того, что в таблицах разная гранулярность (для orders строка = один заказ, для order_items строка = одна из многих позиций в заказе, для payments строка = один факт оплаты из многих по заказу), прямое соединение без предварительной агрегации размножает записи, т.к. соединение происходит не по уникальным атрибутам. DISTINCT в таком случае не решает проблему, т.к.:
1. дубли по order_id в order_items и payments - это не дублирование данных по товарам и платежам, у этих данных другой смысл
2. при прямом соединении по дублирующимся значениям происходит cross join - получается декартово произведение, когда каждая строка соединяется с каждой строкой с таким же идентификатором, получается количество комбинаций 1 (запись в orders) * 2 (order_items) * 2 (payments) = 4 строки

Для корректного результата необходимо предварительно сгруппировать данные по позициям и платежам до той же гранулярности, что и в заказе, т.е. до одного заказа - по order_id, тогда соединение даст правильный результат и записи не будут замножены.

## Правила источников
### Договор с источником платежей
Одна запись CSV - один состоявшийся платёж. Кодировка UTF-8 без BOM, разделитель точка с запятой, символ кавычек ". Перенос строки внутри комментария допустим. Порядок колонок может отличаться. <br />
Заголовок должен содержать ровно семь указанных ниже уникальных имён. Отсутствующее, дополнительное или повторяющееся имя, другой регистр и пробелы в имени колонки считаются ошибкой файла. <br />

| Исходное поле | Поле результата | Правило |
|-----|---|---|
|Payment ID | payment_id | Непустая строка после strip(). Ведущие нули сохраняются |
|Amount | amount | Decimal. Целое или 1-2 знака после запятой. Значение > 0 и <= 9999999999.99 |
|Currency | currency | Убрать крайние пробелы, привести к верхнему регистру. Допустимо только EUR |
| Created At | created_at | Момент создания платежа: ISO 8601 с явным смещением от UTC |
|Paid At |paid_at |Момент оплаты в том же формате. Не раньше created_at |
|Status |status |После strip() и casefold(): paid или оплачен. Оба значения преобразуются в paid |
|Comment |comment |Строка, в том числе пустая. Сохранить содержимое без изменений |

Все значения, кроме комментария, обязательны. В сумме разрешены только цифры и необязательная десятичная запятая: без знака, пробелов внутри числа, разделителей тысяч, экспоненты и обозначения валюты. Точка в сумме этого CSV недопустима. Лишние десятичные знаки отклоняются, округлять их нельзя. <br />
При преобразовании сумм убираются только крайние пробелы. Моменты времени переводятся в UTC. Не подставляется текущая дата, ноль или иной статус вместо ошибочного значения. 

#### Повторы и допуск к загрузке <br />
Если очищенный Payment ID встречается в файле несколько раз, отклоняются все записи с этим ключом, включая совпадающие. Считаются ключи по всем записям с непустым идентификатором, даже если другие поля ошибочны. <br />
Для платежей допускается не более 2% отклонённых записей. Ровно 2% разрешены. Пустой набор или превышение порога запрещает запись в БД. Причины отклонений сохраняются до проверки порога. <br />
Платёж является неизменяемым событием. Повтор уже известного БД ключа разрешён только при совпадении всех семи подготовленных полей. Изменение любого значения требует ошибки и отката текущей загрузки.<br />

### Договор с источником заказов
Корень документа - объект с полями export_date и orders. orders должен быть массивом. Дата выгрузки описывает поставку и не является датой заказа. Идентификаторы заказов в корректной части предоставленных файлов не повторяются. <br />

|Поле |Тип и правило |
|---|---|
|order_id | Непустая строка; крайние пробелы удаляются |
|customer |Обязательный объект |
|customer.customer_id| Непустая строка, ведущие нули сохраняются| 
|items |Обязательный массив; пустой массив разрешён |
|items[].line_no |Положительное целое число, уникальное внутри заказа |
|items[].sku |Непустая строка; крайние пробелы удаляются |
|items[].quantity |Положительное целое число |
|items[].unit_price |Строка с целым числом или 1-2 знаками после точки. Цена > 0 и <= 9999999999.99 |

Все цены указаны в EUR. Обязательные значения не могут быть null. Для unit_price удаляются крайние пробелы, проверяется формат и используется Decimal. Здесь десятичный разделитель точка: правила платёжного CSV с запятой к этому источнику не относятся.<br />

#### orders.json 
Если нарушена структура или значение любого заказа, отклоняется весь документ и не публикуется подготовленный результат. Заказ с пустым items считается корректным и даёт ноль строк позиций.<br />

#### orders_stream.jsonl 
Пустая физическая строка пропускается и учитывается отдельным счётчиком. Она не считается принятым или отклонённым заказом. <br />
Ошибка JSON или нарушение правил заказа отклоняет всю текущую строку. Не записывается часть позиций заказа, если одна из его позиций некорректна. Для этого потока бизнес разрешает отдельные отклонения без порога 2%. Ошибки чтения или записи самого файла останавливают обработку.<br />

>Почему ON CONFLICT DO NOTHING само по себе недостаточно? <br />

В загрузчике конфликт определяется по payment_id - предотвращается вставка еще одной строки с существующим ключом, но не проверяется равенство остальных полей события. Сравнение полей нужно для того, чтобы подтвердить, что повторный ключ обозначает то же неизмененное событие. Если хотя бы одно подготовленное значение отличается, то это конфликт, который должен остановить загрузку.

>Почему проверка только количества и суммы пропустила бы изменение времени в конфликтном файле? <br />

Количества строк и сумма amount не зависит от значений времени, тогда как время created_at и paid_at также являются описательными атрибутами в строке и требуют проверки

>Чем повтор ключа внутри одного источника отличается от повторной доставки уже загруженного события?<br />

Повтор ключа внутри одного источника - нарушение правила уникальности источника, по требованиям отклоняются все записи с повторяющимся ключом. <br />
Повторная доставка уже загруженного события - ситуация между разными запусками, в новом файле приходит строка, которая уже есть в базе, повторная вставка не производится.

## Задание 3

```py
records_list, stats = read_all_pages(url, headers, params, run_id)

order_rows = []
item_rows = []

accepted_orders = 0
accepted_items = 0
accepted_total_amount = 0
rejected_orders = 0

for record in records_list:
    raw = record["raw"]
    try:
        order_row, items = order_process(raw)
    except ValueError as error:
        #сохранение отклоненых записей
        rejected_row = {
            "run_id": run_id,
            "raw_response_id": record["raw_response_id"],
            "page_number": record["page_number"],
            "row_number": record["row_number"],
            "reason": str(error),
            "raw_order": raw,
        }

        target_rejected.parent.mkdir(parents=True, exist_ok=True)
        with target_rejected.open("a", encoding="utf-8") as file:
            file.write(
                json.dumps(rejected_row, ensure_ascii=False) + "\n"
            )
        rejected_orders += 1
    else:
        order_rows.append(order_row)
        item_rows.append(items)

        accepted_orders += 1
        accepted_items += len(items)
        accepted_total_amount += order_row["total_amount"]

if accepted_orders + rejected_orders != stats["received"]:
    raise RuntimeError("Нарушен баланс записей")

print(f"Получено из api: {stats["received"]}")
print(f"Принято заказов: {accepted_orders}")
print(f"Позиций у принятых заказов: {accepted_items}")
print(f"Сумма принятых заказов: {accepted_total_amount}")
print(f"Отклонено заказов: {rejected_orders}")
```

### Правила версий и обработки повторов
* новый ключ: вставка;
* более новое время: обновление заказа и замена его полного набора позиций в одной транзакции;
* более старое время: пропуск;
* одинаковое время и одинаковые подготовленные бизнес-поля и позиции: пропуск;
* одинаковое время, но разные подготовленные бизнес-поля или позиции: конфликт, остановка запуска и откат его изменений.

В практике максимум три попытки одного GET-запроса **включая первую**. Для временных сетевых ошибок, тайм-аутов и 500/502/503/504 паузы перед повторами 1 и 2 секунды. Для 429 пауза не меньше одновременно соответствующей базовой паузы и полученного `Retry-After`; учебный сервер возвращает целые секунды. Ошибки 400/401/403/404, неверный JSON и структура не повторяются автоматически.

Используется одна транзакция данных на весь небольшой запуск. Запись `running` в `load_runs` создаётся и фиксируется до неё. Изменения заказов и позиций, отметка завершённого периода и успешный статус фиксируются вместе только после полного обхода и сверки. При ошибке транзакция данных откатывается; затем отдельной транзакцией обновляется исходная запись запуска до `failed`.

Архив HTTP-ответов и файлы отклонений лежат вне этой транзакции и сохраняются для разбора. По ним нельзя считать данные загруженными. Весь период может быть успешно завершён с отклонёнными заказами, если каждая запись классифицирована и все отклонения сохранены: это явно принятое правило данного кейса.

`load_state.completed_to` хранит верхнюю исключённую границу последнего успешно обработанного периода. Обновляется только вместе с успешными данными; не уменьшается при повторной загрузке старого периода. Если граница не изменилась, её прежний `run_id` тоже сохраняется. Загрузка с тестовым фильтром `status` не обновляет общий прогресс всех заказов.

#### Проверки данных (нет ошибок => 0 записей в результатах)
```sql
--уникальность ключей
select source_system, source_account_id, order_id, count(*) 
from de5_hw.orders
group by source_system, source_account_id, order_id 
having count(*) > 1
;
select source_system, source_account_id, order_id, line_id, count(*)
from de5_hw.order_items
group by source_system, source_account_id, order_id, line_id
having count(*) > 1
;
-- отсутствие позиций без заказа
SELECT i.*
FROM de5_hw.order_items AS i
WHERE NOT EXISTS (
    SELECT 1
    FROM de5_hw.orders AS o
    WHERE o.source_system = i.source_system
      AND o.source_account_id = i.source_account_id
      AND o.order_id = i.order_id
)
;
-- совпадение суммы позиций с total_amount каждого заказа
SELECT
    o.source_system,
    o.source_account_id,
    o.order_id,
    o.total_amount,
    COALESCE(
        SUM(i.quantity * i.unit_price),
        0
    ) AS items_amount
FROM de5_hw.orders AS o
LEFT JOIN de5_hw.order_items AS i
    ON i.source_system = o.source_system
    AND i.source_account_id = o.source_account_id
    AND i.order_id = o.order_id
GROUP BY
    o.source_system,
    o.source_account_id,
    o.order_id,
    o.total_amount
HAVING o.total_amount IS DISTINCT FROM
    COALESCE(SUM(i.quantity * i.unit_price), 0)
;
```
