## Путь данных
**Постановка задачи**: Интернет-магазин хранит заказы в базе данных, получает платежи через API, а возвраты выгружает в CSV. Руководителю нужен ежедневный отчёт о заказах, платежах и возвратах за предыдущий день.

1. Источники - API платежей, CSV с возвратами, данные по заказам из БД
2. Загрузка данных из источников - настройка регулярной загрузки данных в хранилище
3. Staging - промежуточный слой для предварительной подготовки данных к последующей обработке - очистка, дедубликация, приведение данных к единому виду
4. DWH - объединение и хранение согласованных данных по заказам, платежам и возвратам, выстроенные в аналитическую модель
5. Трансформации - преобразования данных, например объединение заказов и оплат по ключу, расчеты сумм и количества и прочие расчеты
6. Витрина - набор связанных таблиц с данными по конкретной предметной области для дальнейшего использования в построении отчетов
7. Отчет - сводные данные для дальнейшего анализа

Для текущей задачи предварительно выбираем **ELT** подход, т.к. можно выгрузить данные источников из БД, csv, API в базу и хранить в исходном виде, а уже после выполнять их очистку, объединение и преобразование непосредстенно в хранилище. Этот подход позволит сохранить исходную детализацию для будущих иных аналитических задач.

| Роль               | Задача        |
| ------------------ |:-------------:|
| Data Engineer      | Настройка регулярной загрузки в хранилище данных платежей через API, возвратов из CSV, заказов из БД |
| Analytics Engineer | Построение модели данных хранилища и подготовка витрины интернет-магазина|
| Data Analyst       | Формирование требований к показателям и построение ежедневного отчета на основе витрины |

**Вопросы для уточнения инженером:**
* У разработчика API платежей: Время готовности источников к загрузке, частота обновления, инкремент или фулл, атрибутный состав и типы данных, pk
* У бизнеса: что именно считать заказом, платежом и возвратом, трактовка статусов, содержание и зерно отчета, период отчетного дня, время, к которому нужна итоговая отчетность


### Процесс подготовки поставки:
1. Изменения разрабатываются на DEV-контуре. 
2. Далее проводится тестирование определенной версии решения на TEST-контуре. 
3. После того, как поставка проходит тестирование, она переносится на PROD

Разделение сред позволяет исключить возможное негативное влияние на регламентные процессы на PROD и безболезненно откатить версию до стабильной в случаях, когда это необходимо. На один заказ order_id = 2006 в order_items приходится две позиции с общей суммой 300 EUR:
|order_id|items_amount|item_count|
|--------|------------|----------|
|2006|300.00|2|

В то же время на один заказ приходится две записи с успешной оплатой в payments:
|order_id|paid_amount|paid_count|
|--------|-----------|----------|
|2006|300.00|2|

Из-за того, что в таблицах разная гранулярность (для orders строка = один заказ, для order_items строка = одна из многих позиций в заказе, для payments строка = один факт оплаты из многих по заказу), прямое соединение без предварительной агрегации размножает записи, т.к. соединение происходит не по уникальным атрибутам. DISTINCT в таком случае не решает проблему, т.к.:
1. дубли по order_id в order_items и payments - это не дублирование данных по товарам и платежам, у этих данных другой смысл
2. при прямом соединении по дублирующимся значениям происходит cross join - получается декартово произведение, когда каждая строка соединяется с каждой строкой с таким же идентификатором, получается количество комбинаций 1 (запись в orders) * 2 (order_items) * 2 (payments) = 4 строки

Для корректного результата необходимо предварительно сгруппировать данные по позициям и платежам до той же гранулярности, что и в заказе, т.е. до одного заказа - по order_id, тогда соединение даст правильный результат и записи не будут замножены.

### Новые запросы от бизнеса
#### «Сколько заказ идёт от создания до оплаты и доставки?»
Накапливающий снимок - при появлении новых данных по заказу атрибуты также обновляются.<br /> 
Детализация: одна строка = один заказ, ключ order_id<br /> 
Даты этапов - ordered_at, paid_at, delivered_at, fully_paid_at<br /> 
При нескольких платежах - fully_paid_at = момент, когда накопленная сумма успешных оплат >= сумма заказа<br /> 
Еще не наступившая дата означает, что этап еще не произошел. <br />
При повторных этапах теряется история изменений по уже прошедшим этапам, т.к. статусы будут перезаписываться.<br />

#### «Какие товары должны были иметь ежедневный снимок?»
Таблица ожидаемого покрытия без числовых показателей - допустимые пары складов и товаров <br />
Детализация: одна строка = дата + товар + склад, ключ snapshot_date, warehouse_key, product_key<br />
С фактическими снимками сопоставляется по ключу, те записи, которые не подтягиваются, становятся заметными.<br />

#### «Продажу сопровождали два менеджера; как разделить её сумму?»
Таблица связей заказа и менеджеров
Детализация: одна строка = одна позиция заказа + менеджер, ключ order_id, line_no, manager_id<br />
Вес участия - числовое значение, обозначающее процент суммы заказа, отнесенной к менеджеру. Сумма весов по каждой позиции равна 1, распределяемая сумма равна стоимости позиции, умноженной на вес - для корректного расчета суммарного итога по заказу требуется использовать именно ее.

#### de3_dwh.mart_cash_daily
Назначение: ежедневный контроль движения денежных средств по каналам<br />
Потребитель: Финансовый менеджер<br />
Детализация: одна дата × один канал<br />
Ключ: report_date, channel_key<br />
Поля и формулы: <br />
- payment_count - Количество успешных нетестовых платежей<br />
- paid_amount_eur - Сумма этих платежей<br />
- refund_count - Количество подходящих успешных возвратов<br />
- refunded_amount_eur - Сумма этих возвратов по дате возврата<br />
- net_cash_eur - paid_amount_eur - refunded_amount_eur<br />
- avg_payment_eur - paid_amount_eur / payment_count; null при отсутствии платежей<br />

Фильтры: отчетные даты в диапазоне между '2025-09-01' и '2025-09-07' <br />
Дата события: report_date <br />
Часовой пояс: Europe/Berlin <br />
Поведение 0/null: Для отсутствующих событий суммы и количества равны 0, для avg_payment_eur - null при отсутствии платежей<br />
Форма хранения: представление<br />
Правило обновления: при обращении к view данные пересчитываются из фактов<br />
