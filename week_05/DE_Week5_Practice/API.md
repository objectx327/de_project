# NorthCart: контракт учебного API

## Запрос

`GET http://127.0.0.1:8765/v1/orders`

Заголовки: `Authorization: Bearer <значение DE5_API_TOKEN>` и `Accept: application/json`. Тело запроса не требуется. Токен не передаётся в URL. Значение `<...>` в этом описании заменяется содержимым переменной, сами скобки не отправляются.

| Параметр | Обязательный | Правило |
| --- | --- | --- |
| `account_id` | Да | Для выданного доступа: `shop_de` |
| `updated_from` | Да | Нижняя граница `updated_at`, включительно |
| `updated_to` | Да | Верхняя граница `updated_at`, исключительно; больше нижней |
| `limit` | Нет | Целое от 1 до 5; по умолчанию 4 |
| `cursor` | Нет | В первом запросе отсутствует; затем точное значение `next_cursor` |
| `status` | Нет | `pending`, `paid`, `cancelled` или `refunded`; без параметра все статусы |
| `snapshot` | Нет | Учебный переключатель `initial` или `updated`; по умолчанию `initial` |
| `scenario` | Нет | Учебный сценарий; по умолчанию `normal` |

Даты передаются в ISO 8601 с часовым поясом, например `2026-09-24T00:00:00Z` или `2026-09-24T02:00:00+02:00`. Отбор идёт по моменту изменения `updated_at`, не по `created_at`. Неизвестные, повторяющиеся и некорректные параметры возвращают 400. Для основной загрузки не задавайте фильтр `status`: иначе будут потеряны другие состояния заказа.

Курсор является непрозрачной строкой. Не вычисляйте его из номера страницы. Он относится к конкретным параметрам, снимку и сценарию; при переходе на следующую страницу остальные параметры сохраняются. Повторный запрос этой страницы использует тот же курсор. Снимки учебного сервера не изменяются во время обхода.

## Ответ страницы

Успешный ответ: HTTP 200, JSON-объект. Обязательны:

* `data`: массив заказов;
* `next_cursor`: непустая строка для продолжения либо `null` для завершения;
* `meta`: объект, где `total_count` - неотрицательное целое количество всех записей выбранного набора, включая некорректные, а `snapshot` - имя снимка.

`meta` не содержит заказов. `total_count` служит для сверки и не заменяет проверку `next_cursor`. Набор без событий возвращает `data: []`, `next_cursor: null`, `total_count: 0`. Пустая страница с непустым курсором требует продолжения.

Сортировка: `updated_at`, затем `order_id`. Один снимок содержит не более одной записи на `order_id` внутри аккаунта. Начальная выборка содержит намеренные нарушения контракта записей: загрузчик должен обнаружить их. HTTP 200 не означает, что все записи корректны.

Пример одной записи, не готового ответа всей страницы:

```json
{
  "order_id": "000001",
  "customer": {"id": "C-00001", "segment": "retail"},
  "status": "paid",
  "currency": "EUR",
  "total_amount": "2.75",
  "created_at": "2026-09-20T08:00:00Z",
  "updated_at": "2026-09-24T08:00:00Z",
  "items": [
    {"line_id": "01", "sku": "SKU-001-1", "quantity": 1, "unit_price": "2.75"}
  ]
}
```

## Правила записей

Все восемь полей верхнего уровня в примере обязательны. Новые неизвестные поля допустимы: сохраните их в исходном ответе, подготовленные поля формируйте явно.

* `order_id`: непустая строка. Ведущие нули значимы. Идентификаторы сохраняются без преобразования в числа и без исправления исходных значений. Строка только из пробелов недопустима.
* `customer`: объект или `null`. `null` означает гостевой заказ и преобразуется в `customer_id = None`. У объекта обязателен непустой строковый `id`. Отсутствие `customer`, пустой объект и строка вместо объекта являются ошибками. `segment` не нужен в целевой таблице.
* `status`: точное значение из `pending`, `paid`, `cancelled`, `refunded`. В этой практике не меняйте регистр и не вводите свои соответствия.
* `currency`: `EUR`.
* `total_amount`: строковая неотрицательная сумма в евро. Разрешены цифры и необязательная точка с одной или двумя цифрами после неё; без пробелов, разделителей тысяч, запятой, знака, экспоненты и специальных значений. Преобразуется через `Decimal`, не через `float`. Максимум `999999999999.99` для `numeric(14,2)`.
* `created_at`, `updated_at`: непустые строки ISO 8601 с часовым поясом. После преобразования `updated_at >= created_at`. Сохраните соответствующие моменты времени в `timestamptz`.
* `items`: массив объектов. Пустой массив допустим: заказ сохраняется без позиций, `total_amount` должен быть нулём. `null`, отсутствующее поле и объект вместо массива недопустимы.

Каждая позиция содержит непустые строковые `line_id` и `sku`, целое `quantity` от 1 до 2147483647 и строковое `unit_price` по тем же денежным правилам. Логическое значение `true` не считается целым количеством. `line_id` уникален внутри заказа. Дополнительные поля позиции допустимы.

`total_amount = sum(quantity * unit_price)` для всех позиций заказа, без округления и допусков. Это стоимость состава заказа, а не выручка, выплата или сумма после возврата. При статусе `refunded` сумму не делайте отрицательной. Все записи и контрольные суммы относятся к EUR.

Ошибка хотя бы одного обязательного поля или позиции отклоняет **заказ целиком** вместе с его позициями. Запишите исходный заказ, его номер на странице, `run_id`, `raw_response_id` и причину; остальные корректные заказы страницы обрабатываются. Ошибка структуры страницы, JSON или HTTP требует правил задания 6 и не превращается в отклонение одной записи.

## Состояния источника и повторы

`initial` содержит 18 записей с `updated_at` от 24 до 26 сентября 2026 года. `updated` представляет состояние после изменений 27 сентября:

* у `000003` статус изменён на `refunded`;
* у `000008` статус изменён на `paid`, добавлена позиция, изменена сумма;
* появились `000019` и `000020`;
* заказ `000006` исчез из API.

API не передаёт уведомления об удалениях. Инкрементальная выборка не позволяет установить удаление `000006`. Его нельзя автоматически удалять из staging из-за отсутствия в следующем ответе. Учебная практика не требует реализации отдельной синхронизации удалений.

Для текущего состояния ключ заказа: `(source_system, source_account_id, order_id)`. Здесь `source_system = 'northcart'`, `source_account_id = 'shop_de'`. Версии сравниваются по `updated_at`:

* новый ключ: вставка;
* более новое время: обновление заказа и замена его полного набора позиций в одной транзакции;
* более старое время: пропуск;
* одинаковое время и одинаковые подготовленные бизнес-поля и позиции: пропуск;
* одинаковое время, но разные подготовленные бизнес-поля или позиции: конфликт, остановка запуска и откат его изменений.

При сравнении одинаковой версии не учитывайте `run_id`, `received_at`, архивные идентификаторы и неизвестные дополнительные поля. Порядок элементов `items` сам по себе не меняет состав: сравнивайте позиции по `line_id`. При пропуске оставьте существующую строку и её технические поля неизменными.

## Учебные сценарии

Используйте `snapshot=initial`, период `[2026-09-24T00:00:00Z, 2026-09-27T00:00:00Z)`, `limit=4`, без фильтра статуса, если не сказано другое. Независимые сценарии различаются значением `scenario`.

| Сценарий | Что делает сервер | Ожидаемая реакция загрузчика |
| --- | --- | --- |
| `normal` | Обычные страницы | Полный обход, отклонения отдельных записей по контракту |
| `transient_503` | На втором пакете записей один раз 503 | Повторить тот же запрос, затем продолжить |
| `rate_limit_once` | На втором пакете один раз 429 и `Retry-After: 1` | Подождать не менее секунды, повторить тот же запрос |
| `persistent_503` | На втором пакете всегда 503 | После трёх попыток остановить запуск |
| `invalid_json` | На втором пакете HTTP 200 с незавершённым JSON | Остановить без автоматических повторов |
| `wrong_structure` | На втором пакете `data` становится объектом | Остановить без автоматических повторов |
| `missing_cursor` | На втором пакете нет `next_cursor` | Ошибка контракта, не конец выгрузки |
| `cursor_loop` | На втором пакете повторяется входящий курсор | Остановить с ошибкой, не обрабатывать бесконечно |
| `empty_then_data` | Сначала пустая страница с курсором, затем все записи | Продолжить; получить те же 18 записей |
| `new_field` | Добавляется `promotion_note` | Сохранить исходный ответ; бизнес-данные не меняются |
| `timeout_once` | Первый ответ второго пакета задерживается на 1 секунду | При read timeout 0.2 секунды повторить и завершить |
| `conflict_same_version` | У `000001` меняется цена и сумма без изменения `updated_at` | После обычной исходной загрузки обнаружить конфликт и откатить запуск |

Счётчик разового сбоя действует отдельно для сочетания параметров и курсора. Повторная проверка тех же параметров в том же процессе может уже не дать разовую ошибку. Для воспроизведения перезапустите сервер. Изменение `run_id` в клиенте не сбрасывает сервер.

401 проверяется отсутствующим или неверным токеном; 403 - `account_id=another_shop`; 400 - `limit=6`; 404 - неверным путём `/v1/unknown`. Пустой успешный набор проверяется периодом `[2026-10-01T00:00:00Z, 2026-10-02T00:00:00Z)`. Ошибку соединения можно проверить после остановки сервера.

## Повторы запросов и транзакция

В практике максимум три попытки одного GET-запроса **включая первую**. Для временных сетевых ошибок, тайм-аутов и 500/502/503/504 паузы перед повторами 1 и 2 секунды. Для 429 пауза не меньше одновременно соответствующей базовой паузы и полученного `Retry-After`; учебный сервер возвращает целые секунды. Ошибки 400/401/403/404, неверный JSON и структура не повторяются автоматически.

Используйте одну транзакцию данных на весь небольшой запуск. Запись `running` в `load_runs` создаётся и фиксируется до неё. Изменения заказов и позиций, отметка завершённого периода и успешный статус фиксируются вместе только после полного обхода и сверки. При ошибке транзакция данных откатывается; затем отдельной транзакцией обновите исходную запись запуска до `failed`.

Архив HTTP-ответов и файлы отклонений лежат вне этой транзакции и сохраняются для разбора. По ним нельзя считать данные загруженными. Весь период может быть успешно завершён с отклонёнными заказами, если каждая запись классифицирована и все отклонения сохранены: это явно принятое правило данного кейса.

`load_state.completed_to` хранит верхнюю исключённую границу последнего успешно обработанного периода. Обновляйте его только вместе с успешными данными; не уменьшайте при повторной загрузке старого периода. Если граница не изменилась, её прежний `run_id` тоже сохраняется. Загрузка с тестовым фильтром `status` не должна обновлять общий прогресс всех заказов.
